MOBILE-FIRST · PLUS-FRIENDLY · GPT-ORCHESTRATED

GPT Plus + 휴대폰 + PC/서버 한 대로 쌀PT 하는 법

ChatGPT가 작업을 지휘하고, Remote Desktop Commander가 연결된 PC를 조작하고, 코드 수정이 필요할 때만 Codex를 호출합니다. 실행 결과를 다시 읽어 PASS/FAIL을 판단하고, 필요한 경우 수정→재실행→재검증을 반복하는 구조입니다.

ChatGPT = 지휘/판정RDC = 손발Codex = 개발Git/Drive = 저장
제작 고지 — 이 페이지의 본문 구성, 문장, 표와 설명용 도표는 GPT를 활용해 작성·제작했습니다. 실제 환경 구성, 실행, 테스트와 벤치마크 수치는 해당 환경에서 직접 확인한 결과를 바탕으로 정리했습니다.

1. 이 구조의 핵심

사용자가 매 단계마다 명령을 복붙하는 구조가 아니라, 처음에 원하는 결과를 말하면 ChatGPT가 연결된 도구를 이용해 작업을 진행하고 결과를 다시 읽어 다음 행동을 결정합니다.

한 번 요청하고 결과만 받는 흐름 — 한 번 목표와 완료 조건을 전달하면, 중간 과정마다 사용자가 다시 답하거나 명령을 복붙하지 않아도 가능한 범위에서 실행·수정·검증 루프를 이어갑니다. 단, 같은 오류가 반복되거나 권한·위험도가 높은 작업이 필요하면 자동 진행을 멈추고 사용자 확인을 받습니다.
1

요청

사용자가 목표와 원하는 결과를 자연어로 전달합니다.

2

확인

ChatGPT가 RDC로 파일·환경·로그·Git 상태를 확인합니다.

3

수정·실행

코딩이 필요하면 Codex, 단순 실행·테스트는 RDC를 사용합니다.

4

판정·루프

결과를 다시 읽고 PASS면 종료, FAIL이면 필요한 수정만 반복합니다.

사용자 요청
   ↓
ChatGPT: 작업 범위 + 완료 조건 결정
   ↓
RDC: 파일/환경/로그 확인
   ↓
코드 수정 필요? ── 예 → Codex 수정
   │                    ↓
   └──── 아니오 ─→ RDC 실행/테스트
                         ↓
              ChatGPT가 결과 다시 읽기
                    ↓         ↓
                  PASS       FAIL
                    ↓         ↓
                 결과 보고 ← 수정 후 재실행 ↺
무한 루프는 아닙니다. 완료 조건, 최대 재시도 횟수, 같은 오류 반복 시 중단 규칙을 두고, 판단이 애매하거나 위험한 변경이 필요하면 자동 수정을 멈추고 사용자에게 보고하는 편이 안전합니다.

2. 각 도구는 무엇을 하는가

ChatGPT — PM / 검증자요청 해석, 작업 분해, 완료 조건 설정, RDC와 Codex 선택, 결과 판정과 다음 행동 결정을 담당합니다.
RDC — 빠른 손발파일 읽기·쓰기, 터미널 명령, Git 상태 확인, 테스트 실행, 로그와 프로세스 확인처럼 deterministic한 작업을 담당합니다.
Codex — 코드 개발자새 코드 작성, 버그 원인 분석, 리팩터링, 여러 파일을 함께 수정하는 작업처럼 추론이 필요한 코딩을 담당합니다.
연결된 PC/서버 — 실행 환경구형 노트북일 필요가 없습니다. 평소 쓰는 데스크톱, 남는 노트북, 직접 관리하는 서버나 VM에서 실행할 수 있습니다.
Git / GitHub — 코드와 이력commit, branch, diff, 테스트 이력을 남겨 어떤 코드가 사용됐는지 추적합니다.
Google Drive — 선택적 결과 저장소대형 데이터, 로그, 실행 결과처럼 Git에 넣기 불편한 파일이 많을 때 함께 사용할 수 있습니다.
핵심은 “RDC가 Codex를 대체한다”가 아니라, 생각할 필요 없는 작업은 RDC에 맡기고 생각이 필요한 코딩에만 Codex를 쓰는 것입니다.

3. 최소 구성 — 무엇이 있어야 하나

최소 구성 — ChatGPT Plus + 작업할 PC/서버 1대 + Remote Desktop Commander면 시작할 수 있습니다. Codex, Git, Google Drive는 목적에 따라 추가하면 됩니다.

사용 가능한 실행 기기

현재 쓰는 데스크톱, 남는 노트북, 오래된 PC, 직접 관리하는 외부 서버나 VM 모두 가능합니다. 중요한 것은 기기가 켜져 있고 RDC agent가 실행 중이어야 한다는 점입니다.

휴대폰은 지휘 화면

휴대폰 ChatGPT에서 자연어로 요청하고, 실제 파일·터미널·코드 실행은 연결된 PC/서버에서 수행합니다. PC 화면을 직접 보지 않아도 되는 작업을 늘리는 것이 목적입니다.

4. 처음부터 따라 하기

① Node.js 준비

제어할 PC/서버에 Node.js 18 이상을 설치하고 터미널에서 확인합니다.

node -v

Node.js 공식 다운로드

② RDC remote agent 실행

npx @wonderwhy-er/desktop-commander@latest remote

브라우저 인증 화면에서 기기를 승인하고 터미널에 Device ready가 표시되는지 확인합니다.

③ ChatGPT에서 RDC 연결

ChatGPT의 앱/커넥터에서 Remote Desktop Commander를 추가하고 안내에 따라 연결합니다. Remote MCP를 직접 연결할 경우 endpoint는 아래와 같습니다.

https://mcp.desktopcommander.app/mcp

④ 처음에는 읽기 전용으로 테스트

연결 직후에는 상태를 바꾸지 않는 요청으로 확인하는 것이 좋습니다.

연결된 컴퓨터에서 Node.js 버전을 확인해주세요.
현재 디렉터리의 파일 목록만 보여주세요.
이 저장소의 git status만 확인해주세요.

⑤ 코드 작업까지 하려면 Codex 추가

연결된 PC에 Codex CLI를 설치합니다.

npm i -g @openai/codex

로그인 후에는 ChatGPT가 RDC를 통해 Codex CLI를 호출하고, 수정 결과를 다시 RDC로 테스트·검증하는 흐름을 만들 수 있습니다. 단순 확인이나 실행은 Codex 없이 RDC만 사용하면 됩니다.

⑥ Git과 Drive는 선택적으로 추가

작업 규모가 작으면 Git 하나로 코드·문서·설정·작은 결과까지 모두 관리해도 됩니다. 대용량 데이터나 자주 갱신되는 로그가 많다면 Google Drive 같은 별도 저장소를 함께 쓰는 편이 관리하기 쉽습니다.

5. 실제로 이렇게 요청합니다

RDC만으로 끝나는 작업

“이 저장소의 변경 파일만 확인해주세요.”
“테스트를 실행하고 실패한 항목만 알려주세요.”
“로그 마지막 100줄을 읽고 원인을 요약해주세요.”

Codex까지 쓰는 작업

“테스트를 실행하고 실패 원인을 확인한 뒤, 코드 수정이 필요하면 Codex에 맡기고 다시 테스트해주세요.”
“이 기능을 구현하고 테스트가 통과할 때까지 수정→검증을 반복해주세요.”

이때 ChatGPT가 매번 무조건 Codex를 호출하는 것이 아니라, 먼저 RDC로 현재 상태를 확인한 뒤 실제 코딩이 필요한 경우에만 Codex로 넘기는 것이 핵심입니다.

6. 저장은 Git만 써도 되고, Drive를 섞어도 됩니다

Git-only

코드, 문서, 설정, 작은 결과 파일 위주라면 Git/GitHub 하나로 충분합니다. 버전과 변경 이력을 한곳에서 관리할 수 있어 가장 단순합니다.

Git + Google Drive

큰 데이터, 긴 로그, 바이너리 결과처럼 저장소를 빠르게 키우는 파일이 많다면 Git은 코드, Drive는 큰 실행 결과로 나누는 방식이 편합니다.

Google Drive를 같이 쓰는 경우

Windows/macOS에서는 Google Drive for desktop을 설치하고 사용할 계정으로 로그인합니다.

파일 스트리밍

파일은 주로 클라우드에 두고 필요할 때 내려받습니다. 로컬 디스크를 아끼고 싶을 때 적합합니다.

파일 미러링

Drive 파일을 로컬에도 항상 보관합니다. 자동화 스크립트가 같은 경로의 파일을 자주 읽고 쓰거나 오프라인에서도 파일이 필요하면 단순합니다.

Drive for desktop의 환경설정에서 파일 스트리밍 또는 미러링을 선택하면 됩니다. Linux에는 공식 Drive for desktop 앱이 없으므로 외부 Linux 서버에서는 Git 중심으로 구성하거나 별도의 동기화 방법을 사용하는 편이 자연스럽습니다.

7. 왜 Codex 하나로 전부 하지 않는가

Codex도 파일을 읽고 터미널을 실행하고 테스트할 수 있습니다. 사용량에 여유가 있고 하나의 에이전트로 모든 것을 처리하는 단순함이 더 중요하다면 Codex만 쓰는 방법도 충분히 합리적입니다.

이 구조를 쓰는 이유는 가능 여부가 아니라 자원 배분입니다. 파일 하나 읽기, git status, 로그 확인처럼 추론이 거의 필요 없는 작업까지 매번 AI 에이전트를 거치지 않는 것입니다.

같은 단순 작업실행 시간inputcached / uncachedoutput
RDC persistent0.663초—Codex agent allowance 0—
Codex Luna / low25.69초42,53337,120 / 5,413224
Codex Astra / low49.11초33,19828,800 / 4,398115

비교 작업은 bench_target.txt 읽기 + git status --porcelain이었습니다. 특정 시점·네트워크·서버 상태의 end-to-end 실측이므로 모델 자체의 절대 성능 benchmark가 아닙니다. Astra는 추가 시도에서 서버 capacity 오류도 발생했으므로 49.11초를 일반적인 속도로 단정하지 않습니다.

“RDC는 토큰을 안 먹는다”의 정확한 의미 — RDC로 직접 실행한 deterministic 작업은 Codex agent usage를 소비하지 않는다는 뜻입니다. ChatGPT 대화 자체의 모델 처리까지 0이라는 의미는 아닙니다.

8. 상시 원격으로 쓰려면

RDC가 설치돼 있어도 실행할 PC가 꺼져 있거나 절전 상태라면 원격 작업을 진행할 수 없습니다. 장시간 원격으로 사용할 기기라면 전원과 절전 설정, RDC agent 실행 상태를 함께 관리해야 합니다.

집 PC / 노트북

전원 연결 상태에서 절전 진입을 막고, 필요하면 RDC agent를 자동 시작하도록 구성합니다. 노트북 덮개를 닫을 때 절전되는 설정도 확인합니다.

외부 서버 / VM

24시간 동작시키기 쉽지만, 최소 권한 계정과 별도 작업 디렉터리를 사용하고 인증정보가 불필요하게 노출되지 않도록 범위를 제한합니다.

9. 연결이 안 될 때 30초 체크

RDC 쪽

Device ready가 떠 있는지 → agent 프로세스가 살아 있는지 → PC가 절전 상태가 아닌지 → 여러 기기가 연결돼 있다면 대상 기기가 맞는지 확인합니다.

ChatGPT 쪽

Remote Desktop Commander가 연결된 상태인지 → 먼저 읽기 전용 요청이 동작하는지 → 그다음 테스트 실행 → 마지막에 파일 수정 순서로 범위를 넓혀 봅니다.

10. 안전하게 쓰는 기본 원칙

RDC는 연결된 컴퓨터에서 현재 사용자 권한으로 파일과 터미널을 다룹니다. 신뢰하는 기기만 연결하고 MFA를 사용하며, 외부 서버에서는 최소 권한 계정과 전용 작업 폴더를 사용하는 편이 좋습니다.

자동 수정 루프에는 완료 조건·최대 재시도·중단 조건을 둡니다. 같은 오류가 반복되거나 삭제·배포·결제·실서비스 변경처럼 영향이 큰 작업이 필요해지면 자동 진행을 멈추고 사람의 확인을 받는 구조가 안전합니다.

처음에는 읽기 전용 확인 → 테스트 실행 → 제한된 파일 수정 → 더 큰 자동화 순서로 확장하는 것이 좋습니다.

11. 그래서 어떤 사람에게 맞는가

잘 맞는 경우

휴대폰에서 PC 작업을 자주 지시하고 싶은 경우, 반복적인 파일·로그·테스트 작업이 많은 경우, Codex 사용량을 코딩에 집중하고 싶은 경우, 장시간 로컬/서버 실행을 관리하고 싶은 경우입니다.

굳이 필요 없는 경우

Codex 사용량에 여유가 충분하고 하나의 에이전트가 모든 터미널·코딩 작업을 처리하는 단순함이 더 중요하다면 Codex 단독 방식이 더 편할 수 있습니다.

12. 한 줄 요약

사용자 요청 → ChatGPT 지휘 → RDC 확인/실행 → 필요할 때 Codex 수정 → RDC 재테스트 → ChatGPT 결과 판정 → PASS가 날 때 종료.

농담 섞어 부르면 “쌀PT”입니다. 비싼 AI를 무조건 덜 쓰는 것이 아니라, 추론은 추론이 필요한 곳에 쓰고 단순 실행은 빠른 도구에 맡기는 구조입니다.

콘텐츠 제작: 본문 구성, 문장, 표와 설명용 도표는 GPT를 활용해 작성·제작했습니다.

실측: 환경 구성, 실제 명령 실행, 테스트와 벤치마크 수치는 해당 개발 환경에서 확인한 결과를 바탕으로 정리했습니다.

개인 계정 정보, 로컬 경로, 인증정보 등은 공개 페이지에 포함하지 않습니다.
